## Практическое занятие №19
### Работа с реляционными СУБД на примере PostgreSQL

1. **Цель работы**  
   Целью практического занятия было изучение принципов работы с реляционной СУБД PostgreSQL и подключение базы данных к серверному приложению на Node.js. В ходе выполнения требовалось понять отличие реляционной модели данных от нереляционной, освоить работу с таблицами, связями, SQL-запросами и CRUD-операциями через backend-приложение.

2. **Выполненные действия**  
   В рамках практики было создано серверное приложение на Node.js с использованием Express. Для подключения к PostgreSQL использовались библиотеки `pg` и/или ORM `Sequelize`. Была определена сущность пользователя с полями `id`, `first_name`, `last_name`, `age`, `created_at`, `updated_at`. Также была реализована логика работы с таблицей пользователей: создание записей, получение списка пользователей, получение пользователя по идентификатору, обновление данных и удаление записи.

3. **Проверка результата**  
   Работоспособность приложения проверялась через HTTP-запросы к маршрутам `/api/users`, `/api/users/:id` с использованием методов `POST`, `GET`, `PATCH`, `DELETE`. При создании пользователя данные сохранялись в PostgreSQL, при чтении возвращались из базы данных, при обновлении изменялись в таблице, а при удалении удалялись из постоянного хранилища. Также была проверена корректность обработки ошибок при обращении к несуществующему пользователю.

4. **Вывод**  
   В результате выполнения практического занятия были закреплены навыки подключения PostgreSQL к backend-приложению, построения REST API и выполнения CRUD-операций с использованием реляционной базы данных. Практика показала, что PostgreSQL удобно применять в задачах, где важны строгая структура данных, связи между таблицами, уникальность значений и надежное хранение информации.

## Практическое занятие №20
### Работа с NoSQL СУБД на примере MongoDB

1. **Цель работы**  
   Целью практического занятия было изучение принципов работы с NoSQL-базами данных на примере MongoDB и подключение документоориентированной базы данных к Node.js-приложению. Особое внимание уделялось отличию MongoDB от реляционных СУБД: отсутствию жесткой схемы таблиц, хранению данных в виде документов и гибкости структуры.

2. **Выполненные действия**  
   В ходе работы было создано серверное приложение на Node.js и Express. Для взаимодействия с MongoDB использовалась библиотека `mongoose`, позволяющая описывать схемы документов и выполнять операции с коллекциями. Была создана модель пользователя с полями `first_name`, `last_name`, `age`, `created_at`, `updated_at`. Для данной модели были реализованы маршруты создания, чтения, обновления и удаления пользователей.

3. **Проверка результата**  
   Проверка выполнялась путем отправки запросов к маршрутам `/api/users` и `/api/users/:id`. При запросе `POST /api/users` создавался новый документ пользователя в MongoDB. Запрос `GET /api/users` возвращал список всех пользователей, `GET /api/users/:id` позволял получить конкретного пользователя, `PATCH /api/users/:id` изменял данные документа, а `DELETE /api/users/:id` удалял пользователя из коллекции. Дополнительно проверялась связь каждого маршрута именно с NoSQL-базой данных, а не с временным массивом в памяти приложения.

4. **Вывод**  
   В результате выполнения практики были изучены особенности документоориентированного хранения данных и работа с MongoDB через Mongoose. Практика показала, что MongoDB хорошо подходит для приложений, где структура данных может меняться, а разработчику требуется быстро создавать и изменять модели без жесткой схемы таблиц.

## Практическое занятие №21
### Кэширование с использованием Redis

1. **Цель работы**  
   Целью практического занятия было изучение механизма кэширования данных с использованием Redis. В рамках работы требовалось понять, как кэш помогает ускорять ответы сервера, снижать нагрузку на основную базу данных и уменьшать количество повторяющихся запросов к backend-логике.

2. **Выполненные действия**  
   В серверное приложение был добавлен Redis как промежуточный слой хранения часто запрашиваемых данных. Были реализованы функции чтения данных из кэша, сохранения ответа в Redis и очистки кэша при изменении данных. Кэширование было добавлено для маршрутов получения списка пользователей, получения пользователя по идентификатору, получения списка товаров и получения товара по идентификатору. Для пользователей было установлено время хранения кэша 1 минута, для товаров — 10 минут.

3. **Проверка результата**  
   Работоспособность кэширования проверялась повторными запросами к одним и тем же маршрутам. При первом запросе данные возвращались сервером из основного источника и сохранялись в Redis с пометкой `source: "server"`. При повторном запросе в течение времени жизни кэша данные возвращались уже из Redis с пометкой `source: "cache"`. Также проверялось, что при изменении или удалении данных соответствующий кэш очищается, чтобы пользователь не получал устаревшую информацию.

4. **Вывод**  
   В результате выполнения практического занятия были получены навыки интеграции Redis в backend-приложение и реализации серверного кэширования. Практика показала, что Redis удобно использовать для ускорения часто повторяющихся операций чтения, особенно в API, где одни и те же данные могут запрашиваться многократно разными клиентами.

## Практическое занятие №22
### Балансировка нагрузки в веб-приложениях

1. **Цель работы**  
   Целью практического занятия было изучение принципов балансировки нагрузки в веб-приложениях. Необходимо было понять, как распределять входящие HTTP-запросы между несколькими backend-серверами, как повысить отказоустойчивость системы и как использовать Nginx и HAProxy в роли программных балансировщиков.

2. **Выполненные действия**  
   В ходе выполнения практики были подготовлены несколько backend-серверов на Node.js, работающих на разных портах. Каждый сервер возвращал ответ с указанием своего порта или идентификатора, что позволяло определить, какой экземпляр обработал запрос. Далее был настроен Nginx с блоком `upstream`, в котором перечислялись backend-серверы. Также была рассмотрена альтернативная настройка балансировки через HAProxy.

3. **Проверка результата**  
   Проверка выполнялась с помощью повторных запросов `curl http://localhost/`. При нескольких последовательных обращениях ответы приходили от разных backend-серверов, что подтверждало распределение нагрузки. Дополнительно были добавлены параметры `max_fails` и `fail_timeout`, после чего проверялась отказоустойчивость: при недоступности одного сервера Nginx временно исключал его из обработки запросов и продолжал направлять трафик на рабочие экземпляры приложения.

4. **Вывод**  
   В результате выполнения практического занятия были изучены основные подходы к балансировке нагрузки и повышению отказоустойчивости backend-приложений. Практика показала, что балансировщик позволяет распределять запросы между несколькими серверами, снижать риск перегрузки отдельного экземпляра и обеспечивать более стабильную работу веб-системы.

## Практическое занятие №23
### Контейнеризация приложений с Docker

1. **Цель работы**  
   Целью практического занятия было изучение контейнеризации приложений с использованием Docker и Docker Compose. Необходимо было понять, как упаковать backend-приложение вместе с зависимостями в Docker-образ, как запускать контейнеры и как объединять несколько сервисов в единую сеть с помощью `docker-compose.yml`.

2. **Выполненные действия**  
   В рамках практики был создан Dockerfile для backend-сервиса на Node.js. Также был подготовлен файл `docker-compose.yml`, описывающий несколько backend-контейнеров и Nginx в роли балансировщика нагрузки. Каждый backend-сервис запускался в отдельном контейнере, а Nginx обращался к ним по именам сервисов внутри Docker-сети. Конфигурационный файл `nginx.conf` был подключен к контейнеру Nginx через volume.

3. **Проверка результата**  
   Весь стек запускался командой `docker compose up --build` в среде WSL. После запуска проверялись работа контейнеров, доступность приложения через `localhost`, корректность маршрутизации запросов через Nginx и распределение запросов между backend-контейнерами. Также проверялась отказоустойчивость: при остановке одного backend-контейнера Nginx переставал направлять на него запросы и продолжал обслуживать трафик через оставшиеся контейнеры.

4. **Вывод**  
   В результате выполнения практического занятия были получены навыки контейнеризации backend-приложений, сборки Docker-образов и запуска многоконтейнерной системы через Docker Compose. Практика показала, что контейнеризация упрощает развертывание проекта, делает окружение воспроизводимым и позволяет удобно запускать несколько компонентов системы одной командой.
